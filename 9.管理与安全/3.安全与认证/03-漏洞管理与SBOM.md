# 漏洞管理与 SBOM

> 解决什么问题：产品上市后能回答“用了什么组件、有没有已知漏洞、怎么修”。
> 不解决：具体漏洞利用/渗透测试。

## 1. SBOM

| 格式 | 说明 |
|---|---|
| SPDX | Linux 基金会，字段全 |
| CycloneDX | OWASP，轻量，适合 CI |
| SWID | 通用标识 |

最小字段：

```text
组件名 / 版本 / 供应商 / 许可证 / 来源 / 哈希 / 依赖关系
```

生成：

```bash
# 示例：syft
syft dir:. -o spdx-json > sbom.spdx.json
syft dir:. -o cyclonedx-json > sbom.cdx.json
```

## 2. 漏洞来源

| 来源 | 用途 |
|---|---|
| NVD | CVE/CVSS |
| 厂商通告 | 芯片/模组/驱动 |
| 发行版安全跟踪 | OpenWrt/Debian |
| GitHub Advisory | 开源组件 |
| 自研扫描 | 配置/代码 |

## 3. 流程

```text
组件清单 → 漏洞匹配 → 可达性/影响评估 → 修复/缓解 → 复测 → 通告
```

### 3.1 匹配

- 用 SBOM 的 CPE/purl 匹配 CVE。
- 注意版本范围/回移补丁（发行版可能已修但版本号未变）。

### 3.2 评估

| 因素 | 问题 |
|---|---|
| CVSS | 基础分 |
| 可达性 | 组件是否被调用/暴露 |
| 权限 | 是否需要登录/物理 |
| 影响 | RCE/信息泄露/DoS |
| 在野 | 是否有利用 |

不要只看 CVSS 分数；不可达的高分漏洞优先级可降。

## 4. 修复策略

| 策略 | 场景 |
|---|---|
| 升级组件 | 有修复版本 |
| 回移补丁 | 不能升级 |
| 配置缓解 | 关闭功能/限权 |
| 网络隔离 | 短期 |
| 接受风险 | 低风险/不可达，需记录 |

修复后必须回归：功能/性能/兼容性。

## 5. 披露与合规

- 内部：漏洞台账、责任人、期限。
- 外部：遵循 CVE/厂商披露约定；不提前公开。
- 合规：SBOM 交付、许可证、出口管制。
- 客户/运营商：安全问卷/渗透测试报告。

## 6. 工具链

```text
构建 → 生成 SBOM → 漏洞扫描 → 门禁 → 归档
```

- 每次发布归档 SBOM + 扫描报告。
- 订阅新 CVE，定期重扫旧版本。
- 记录“已知未修”及理由。

## 7. 常见问题

| 问题 | 说明 |
|---|---|
| SBOM 不全 | 只扫直接依赖 |
| 版本误报 | 回移补丁 |
| 只看看 CVSS | 忽略可达性 |
| 修了没回归 | 引入新问题 |
| 无归档 | 无法追溯 |

## 8. 检查表

- [ ] 构建生成 SBOM。
- [ ] 漏洞扫描/匹配。
- [ ] 可达性评估。
- [ ] 修复/缓解/接受记录。
- [ ] 回归测试。
- [ ] 发布归档。
