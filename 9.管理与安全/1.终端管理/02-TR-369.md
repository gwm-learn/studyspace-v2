# TR-369 / USP

> 解决什么问题：TR-069 之后，运营商如何用 USP 管理 CPE/IoT；与 CWMP 的差异与迁移路径。
> 不解决：具体 Controller 平台实现。

## 1. 角色

| 角色 | 对应 TR-069 | 职责 |
|---|---|---|
| Controller | ACS | 管理端 |
| Agent | CPE 客户端 | 被管理端 |
| Endpoint ID | — | Agent 的全局唯一标识 |
| Broker | — | 消息路由（MQTT 场景） |

## 2. 与 TR-069 的关键差异

| 维度 | TR-069/CWMP | TR-369/USP |
|---|---|---|
| 传输 | HTTP/HTTPS，CPE 主动 | 可双向：WebSocket、MQTT、CoAP、UDS |
| 会话 | 请求/响应 + 空响应结束 | 消息总线，异步 |
| 数据模型 | TR-098/TR-181 | USP 数据模型（兼容 TR-181） |
| 扩展 | 厂商参数 | 路径、对象、事件、操作 |
| 实时性 | 周期/连接请求 | 长连接推送 |
| 多租户 | 弱 | Controller/Broker 支持 |

## 3. 消息模型

| 消息 | 方向 | 作用 |
|---|---|---|
| Get / GetResp | Controller↔Agent | 读 |
| Set / SetResp | Controller↔Agent | 写 |
| Add / AddResp | Controller↔Agent | 增对象 |
| Delete / DeleteResp | Controller↔Agent | 删对象 |
| Operate / OperateResp | Controller↔Agent | 执行命令（重启、诊断） |
| Notify / NotifyResp | Agent→Controller | 事件上报 |
| Event | Agent→Controller | 订阅事件 |

消息头包含 `msg_id`、`msg_type`、`endpoint_id`，支持请求/响应匹配与超时重试。

## 4. MTP（消息传输协议）

| MTP | 特点 | 适用 |
|---|---|---|
| WebSocket | 长连接、双向、穿透较好 | 主流 |
| MQTT | 发布/订阅、适合大规模 | 运营商/IoT |
| CoAP | 轻量 UDP | 受限设备 |
| UDS | 本机 | 进程间 |

选择要点：NAT 后优先 WebSocket/MQTT；需要服务端主动推送时必须有长连接。

## 5. 数据模型与路径

```text
Device.
├── DeviceInfo.
├── WiFi.
├── IP.
├── Hosts.
├── Firewall.
└── ...
```

路径规则与 TR-181 类似；支持 `{i}` 实例、搜索表达式、部分路径读取。

## 6. obuspa 实验环境

[obuspa](https://github.com/BroadbandForum/obuspa) 是 BBF 官方开源 Agent：

```bash
git clone https://github.com/BroadbandForum/obuspa.git
cd obuspa
# 依赖与构建见仓库 README
```

最小验证：
1. 启动 obuspa，配置 Controller 地址与 MTP。
2. 用 Controller/测试工具发 Get。
3. 抓 WebSocket/MQTT 报文，确认 `msg_id` 与响应匹配。
4. 触发一次 Notify，确认事件到达。

## 7. 迁移建议

1. 先梳理 TR-069 的参数树与 RPC 使用面。
2. 建立 TR-181 ↔ USP 路径映射。
3. 保留 TR-069 双栈过渡（很多运营商仍要求）。
4. 先做 Get/Set/Notify 三个最小闭环，再做 Operate/固件升级。
5. 安全：mTLS、证书轮换、Endpoint ID 防伪造。

## 8. 常见问题

| 现象 | 首查 |
|---|---|
| 连不上 Controller | MTP 地址/端口、证书、NAT、DNS |
| 消息无响应 | `msg_id` 不匹配、超时、Agent 未订阅 |
| 路径不存在 | 数据模型版本、实例路径 |
| Notify 丢失 | 订阅未建立、重连后未恢复 |
| 升级失败 | 下载 URL、校验、分区、回滚 |
