# 应用层协议


## DNS 协议详解


### 1. 概述：域名系统与层次化命名空间

DNS（Domain Name System，域名系统）将人类易记的域名（如 `www.example.com`）映射为机器可用的 IP 地址。它替代了早期 NIS/`/etc/hosts` 单一静态文件的方案，核心规范为 **RFC 1034**（概念）与 **RFC 1035**（实现细节）。

DNS 采用**分布式、层次化的命名空间**，域名由**点分标签（Label）**组成，从右向左级别递减：

```
                 .                          ← 根域（root，一个"点"）
                 ├── com  .org  .net        ← 顶级域 TLD（.com/.org/国家域 .cn/.jp）
                 │    └── example            ← 二级域
                 │         └── www           ← 主机名（三级及以下）
```

| 层级 | 示例 | 职责 |
|------|------|------|
| **根域** | `.` | 全球 13 组根服务器（Root Server，A~M 节点），只负责指引顶级域 |
| **顶级域 TLD** | `.com` `.org` `.cn` | 通用顶级域（gTLD）与国家顶级域（ccTLD），由 ICANN 授权管理机构运营 |
| **二级域** | `example.com` | 注册者向注册商购买的域名，可在其下自由划分 |
| **主机名** | `www.example.com` | 域内具体主机，由域管理员维护 NS 记录指向的权威服务器 |

> 域名解析是**从右往左**逐级下探的过程：先问根服务器"`.com` 归谁管"，再问 `.com` 服务器"`example.com` 归谁管"，最后问 `example.com` 的权威服务器"`www` 的 IP 是什么"。每级只负责自己范围内的**下一级**，这就是"层次化"的本质。

DNS 默认基于 **UDP 53 端口**传输（报文小、开销低），报文超过 512 字节或需区域传送（AXFR/IXFR）时改用 **TCP 53**。

### 2. 解析流程：递归查询 vs 迭代查询

解析动作分两类角色：**递归解析器（Recursive Resolver）**负责替客户端"跑腿"，**权威服务器（Authoritative Server）**只回答自己管辖域内的记录。

| 查询方式 | 发起者 | 行为 | 特点 |
|----------|--------|------|------|
| **递归查询** | 客户端 → 本地解析器 | 解析器必须给出**最终答案**，查不到就替客户端逐级去问 | 对客户端透明，结果确定 |
| **迭代查询** | 解析器 → 各级服务器 | 服务器只回答"下一级该找谁"，**不代查**，由请求方自己继续问 | 服务器无状态、压力小 |

```
客户端              本地递归解析器           根服务器          .com服务器       example.com权威
  │  ①递归查询          │                     │               │               │
  │ ─────────────────►  │                     │               │               │
  │                     │  ②迭代：com归谁管？   │               │               │
  │                     │ ──────────────────► │               │               │
  │                     │ ◄── 返回.com服务器地址 │               │               │
  │                     │  ③迭代：example.com归谁管？           │               │
  │                     │ ────────────────────────────────►    │               │
  │                     │ ◄── 返回example.com权威服务器地址 ──── │               │
  │                     │  ④迭代：www的A记录？                                │
  │                     │ ────────────────────────────────────────────────►  │
  │                     │ ◄── 返回www.example.com = 93.184.216.34 ──────────  │
  │ ◄── 最终答案 ─────── │                     │               │               │
```

- 递归解析器通常是运营商/公共 DNS（如 `8.8.8.8`、`114.114.114.114`）或本地路由器
- 权威服务器只做迭代应答，**永远不替别人递归**，这是防止 DDoS 放大（见第 7 章）的关键防线之一
- 真实场景中 ②③④ 步往往**命中缓存**直接返回，客户端体验为毫秒级

### 3. DNS 报文格式

DNS 报文由**头部（Header，固定 12 字节）+ Question + Answer / Authority / Additional** 组成，同一格式适用于查询与应答：

#### 3.1 Header（12 字节）

| 字段 | 长度(位) | 说明 |
|------|---------|------|
| **Transaction ID** | 16 | 事务 ID，客户端随机生成，用它与应答匹配（查询与应答必须一致） |
| **Flags** | 16 | 标志位，见下表 |
| **QDCOUNT** | 16 | Question 区中的问题数，通常为 1 |
| **ANCOUNT** | 16 | Answer 区中的资源记录（RR）数 |
| **NSCOUNT** | 16 | Authority 区中的 RR 数（权威服务器信息） |
| **ARCOUNT** | 16 | Additional 区中的 RR 数（附加信息，如粘附记录） |

Flags 字段各位：

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | **QR** | 0=查询，1=应答 |
| 1~4 | **Opcode** | 0=标准查询，1=反向查询，2=服务器状态查询 |
| 5 | **AA** | 权威应答：应答是否来自权威服务器 |
| 6 | **TC** | 截断：应答超过 512 字节被截断，提示改用 TCP |
| 7 | **RD** | 期望递归：客户端置 1，要求解析器递归查询 |
| 8 | **RA** | 可用递归：服务器声明自己支持递归 |
| 9~11 | Z | 保留位（DNSSEC 时代用于 AD、CD 位） |
| 12~15 | **RCODE** | 应答码：0=NOERROR，1=FORMERR，2=SERVFAIL，3=NXDOMAIN（域名不存在），4=NOTIMP，5=REFUSED |

#### 3.2 Question 区

| 字段 | 长度 | 说明 |
|------|------|------|
| **QNAME** | 变长 | 查询的域名，每个标签前加 1 字节长度前缀，以 0 结尾（如 `www.example.com` → `03www07example03com00`） |
| **QTYPE** | 16 位 | 查询的记录类型（见第 4 章），255=ANY |
| **QCLASS** | 16 位 | 查询类别，通常为 1（IN，Internet） |

#### 3.3 Resource Record（RR）

Answer / Authority / Additional 三个区共用同一种 RR 结构：

| 字段 | 长度 | 说明 |
|------|------|------|
| **NAME** | 变长 | 记录所属域名（应答中常用**压缩指针**指向 Question 的 QNAME 省字节） |
| **TYPE** | 16 位 | 记录类型（见第 4 章） |
| **CLASS** | 16 位 | 类别，通常为 1（IN） |
| **TTL** | 32 位 | 缓存存活时间（秒），见第 5 章 |
| **RDLENGTH** | 16 位 | RDATA 数据长度（字节） |
| **RDATA** | 变长 | 记录数据：A 记录为 4 字节 IPv4，AAAA 为 16 字节 IPv6，其余类型按各自格式 |

### 4. 常见 DNS 记录类型

| 类型 | 名称 | RDATA 内容 | 用途与说明 |
|------|------|-----------|-----------|
| **A** | Address | 4 字节 IPv4 | 域名 → IPv4 地址，最基础的正向解析记录 |
| **AAAA** | IPv6 Address | 16 字节 IPv6 | 域名 → IPv6 地址，可多条并存 |
| **CNAME** | Canonical Name | 目标域名 | 别名记录，指向另一域名（如 `www` → `example.com`）；CNAME 不能与其他记录共存于同一名字 |
| **MX** | Mail Exchanger | 优先级(16位)+邮件服务器域名 | 邮件路由，数值越小优先级越高，多台可做冗余 |
| **NS** | Name Server | 权威服务器域名 | 声明某域由哪些服务器负责，是"下一级怎么找"的依据 |
| **PTR** | Pointer | 目标域名 | **反向解析**：IP → 域名（存放于 `in-addr.arpa` / `ip6.arpa` 特殊域） |
| **SOA** | Start of Authority | 主服务器、负责人邮箱、序列号等 | 每个区域唯一一条，描述区域主服务器与刷新参数 |
| **TXT** | Text | 任意文本串 | 可读描述，常用于 SPF/DKIM 邮件验证、域名所有权验证 |
| **SRV** | Service | 优先级+权重+端口+目标主机 | 定位具体服务（如 SIP、LDAP），`_service._proto.domain` 命名 |

补充说明：

- **粘附记录（Glue Record）**：NS 记录指向的域名若在**被管域之下**（如 NS 指向 `ns1.example.com` 且该域自身是 `example.com`），父级会在 Additional 区附带该 NS 的 A 记录，避免"鸡生蛋"的循环依赖；**反向解析 PTR** 把 IP 反写后挂到 `in-addr.arpa` 下（如 `216.34.184.93` → `93.184.34.216.in-addr.arpa`），由 IP 段所有者维护

### 5. 缓存机制（TTL 与各级缓存）

缓存是 DNS 高性能的根基，一切缓存由记录的 **TTL（Time To Live，秒）** 驱动：

| 缓存位置 | 缓存什么 | 特点 |
|----------|----------|------|
| **本地解析器 + OS/应用缓存** | 解析结果（域名→IP） | 客户端本机（如 systemd-resolved）、浏览器各自缓存，命中则无需出网 |
| **递归解析器缓存** | 各权威服务器的应答 | 运营商/公共 DNS 共享给所有用户，命中率最高 |
| **权威服务器自身** | 不缓存（它就是真相源） | 只负责签发带 TTL 的记录 |

关键行为：

- 记录到期（TTL 归零）后**必须丢弃**，重新向上游查询，以感知记录的变更
- TTL 权衡：**太大**则域名/IP 变更后客户端长期拿到旧地址；**太小**则缓存失效频繁、查询压力大。常见 A 记录 TTL 为 300~86400 秒
- **负缓存（Negative Caching）**：NXDOMAIN（域名不存在）等**否定应答**也会被缓存（RFC 2308）；同时递归解析器对权威服务器的 NS 记录往往有自己的**隐含 TTL**（如 2 天），防止权威服务器失联后整个区域"失忆"

> 缓存同时是安全双刃剑：正常场景大幅削减查询流量，但若缓存被**投毒**（见第 7 章），错误结果会在整个 TTL 期内被"广为传播"。

### 6. 加密 DNS：DoH 与 DoT

传统 DNS 明文传输，查询内容与应答可被路径上的任何节点**窥探与篡改**。加密 DNS 在传输层解决该问题：

| 对比项 | **DoT（DNS over TLS）** | **DoH（DNS over HTTPS）** |
|--------|-------------------------|---------------------------|
| RFC | RFC 7858 | RFC 8484 |
| 传输方式 | 独立 **TCP 853** 端口上的 TLS | 复用 **HTTPS 443** 端口，走 HTTP/2 |
| 报文封装 | TLS 记录直接承载 DNS 报文 | DNS 报文作为 HTTPS 的 body（`application/dns-message`） |
| 可观测性 | 独立端口，**可被识别和封锁** | 与普通网页流量混在一起，**难以区分**（隐蔽性更好） |
| 连接管理 | 长连接 + 会话复用 | 依赖 HTTP/2 多路复用 |
| 典型配置 | 路由器/系统级（如 stubby） | 浏览器内置（Chrome/Firefox）、系统级 |
| 防护能力 | 防窃听、防篡改（防中间人） | 同左，额外具备抗封锁能力 |

两者对比一句话：

- **DoT 是"给 DNS 穿上 TLS 外套"**：协议边界清晰，适合网络设备统一管控，但传统防火墙一眼就能识别端口 853 并封锁
- **DoH 是"把 DNS 藏进网页流量"**：浏览器场景部署简单、隐蔽性强，但也带来**解析器集中化**问题（流量集中于大厂 DoH 服务器，隐私反而集中暴露），且绕过网络管理员的审计

> 无论 DoH 还是 DoT，都**只保护 DNS 查询链路本身**，不能替代 **DNSSEC**（对记录做数字签名，防止权威数据被伪造）。两者层次不同：DoH/DoT 保"运输"，DNSSEC 保"数据"。

### 7. 常见 DNS 攻击与防护

| 攻击 | 原理 | 危害 | 防护手段 |
|------|------|------|----------|
| **DNS 劫持（Hijacking）** | 攻击者篡改解析结果，指向钓鱼/恶意服务器（本地劫持、上游被黑、恶意路由器） | 用户访问被重定向，账号密码被钓 | 使用 DoH/DoT 加密链路；核对解析结果；使用可信解析器 |
| **DNS 缓存投毒（Cache Poisoning）** | 向递归解析器注入伪造的应答并**抢答**，让错误记录进入缓存（经典手法：伪造 Transaction ID + 随机源端口 + Kaminsky 攻击） | 错误结果在 TTL 期内毒害所有查询者 | 随机源端口、随机 Transaction ID；**0x20 编码**（域名大小写随机化）；**DNSSEC** 根除 |
| **DNS 放大攻击（Amplification）** | 攻击者伪造受害者 IP 作为源地址，向**开放递归服务器**发送小体积查询（如 ANY、大 TXT），服务器把大体积应答（放大几十倍）打向受害者 | 反射型 DDoS，攻击流量被放大 50~100 倍 | 服务器侧：限制递归开放范围（ACL）、响应速率限制、丢弃 ANY；全网侧：BCP38 源地址验证、关闭开放递归 |

三个关键防线：

- **DNSSEC（RFC 4033~4035）**：权威服务器用私钥对记录签名，解析器用公钥验签，从**数据源头**杜绝伪造，是缓存投毒的根治方案
- **0x20 编码**：递归解析器在查询时随机变换域名的大小写，攻击者若猜不中大小写组合就无法伪造合法应答
- **加密传输（DoH/DoT）**：挡住路径上的**被动窃听与中间人篡改**，与 DNSSEC 互补

## DHCPv4 协议详解


### 1. 概述：DHCPv4在IPv4网络中的角色

DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）的前身是 BOOTP（RFC 951），v4 主规范为 **RFC 2131**，选项定义见 **RFC 2132**。DHCPv4 的核心作用：

- 为 IPv4 主机**动态分配 IP 地址**，免去手工逐台配置
- 同时下发子网掩码、默认网关、DNS 服务器等网络参数
- 通过**租约（Lease）**机制管理地址的分配、续期与回收，实现地址复用

DHCPv4 基于 UDP 传输，**服务器端口 67，客户端端口 68**。客户端在尚未获得 IP 地址时没有可用的源地址，只能以源 IP `0.0.0.0`、目的地址 `255.255.255.255` 的**广播**方式寻找服务器。

#### 1.1 三种地址分配方式（RFC 2131）

| 方式 | 说明 | 适用场景 |
|------|------|----------|
| 动态分配（Dynamic） | 服务器从地址池中挑选地址，有租约，到期回收 | PC、手机等普通终端 |
| 自动分配（Automatic） | 与动态类似，但首次分配后地址固定归该客户端 | 需要地址保持稳定的设备 |
| 手动分配（Manual） | 管理员手工把 MAC 与地址绑定，DHCP 仅下发参数 | 服务器、打印机、网络设备 |

### 2. 四步交互流程（DISCOVER → OFFER → REQUEST → ACK）

客户端上电、接口 UP 后进入 INIT 状态，开始四步交互获取地址：

```
客户端                                          DHCP服务器
  │  ① DHCPDISCOVER（广播）                       │
  │ ───────────────────────────────────────────► │
  │  ② DHCPOFFER（单播或广播）                   │
  │ ◄─────────────────────────────────────────── │
  │  ③ DHCPREQUEST（广播）                       │
  │ ───────────────────────────────────────────► │
  │  ④ DHCPACK（单播或广播）                     │
  │ ◄─────────────────────────────────────────── │
  ▼
绑定完成（BOUND），地址可以使用
```

#### 2.1 DISCOVER：寻找服务器

- 客户端广播发送 DISCOVER，源 IP `0.0.0.0`、源端口 68，目的地址 `255.255.255.255`、目的端口 67
- 关键选项：Message Type(53)=1，可选 Requested IP(50)、Hostname(12)
- 客户端不知道链路内有哪些服务器，DISCOVER 是"谁可以为我提供地址"的广播询问

#### 2.2 OFFER：服务器报价

- 每个收到 DISCOVER 的服务器都会**预留**一个地址并回复 OFFER
- yiaddr 字段填提议的 IP 地址；options 携带 Subnet Mask(1)、Router(3)、DNS(6)、Lease Time(51)、Server Identifier(54)
- 若报文 flags 中的广播位（B 位）置 1，OFFER 用广播发送，否则可单播
- 客户端可能收到**多个** OFFER，一般选择**最先到达**的一个

#### 2.3 REQUEST：选定服务器

- 客户端广播 REQUEST，携带 Server Identifier(54)=选中的服务器 IP，以及 Requested IP(50)=接受提议的地址
- 之所以**仍然广播**：同子网内的其他服务器也能收到该报文，得知"客户端选了别人"，可以**收回**各自预留的地址，避免地址泄漏

#### 2.4 ACK / NAK：服务器确认

- 服务器收到 REQUEST 后确认地址仍可用，回复 **ACK**（Message Type=5），客户端正式进入 BOUND 状态，启动 T1/T2 定时器
- 若地址已被占用或策略不允许，回复 **NAK**（Message Type=6），客户端回到 INIT 状态重新 DISCOVER
- 客户端收到 ACK 后通常做一次 **ARP 冲突检测**：若发现地址冲突，发送 DECLINE(4) 通知服务器

| 阶段 | 报文 | 方向 | 关键内容 |
|------|------|------|----------|
| ① | DISCOVER | 客户端 → 广播 | Message Type=1，请求分配地址 |
| ② | OFFER | 服务器 → 客户端 | yiaddr=提议地址，携带掩码/网关/DNS/租期/Server ID |
| ③ | REQUEST | 客户端 → 广播 | Message Type=3，Server ID=选定服务器，Requested IP |
| ④ | ACK / NAK | 服务器 → 客户端 | Message Type=5 确认 / 6 拒绝 |

> 四步交互的意义在于**多服务器场景**下的协商：DISCOVER/OFFER 让客户端了解各家报价，REQUEST/ACK 完成"唯一归属"确认，避免多个服务器对同一地址重复分配。

#### 2.5 DHCPINFORM：无地址获取参数

已通过静态配置或 PPPoE 等其他方式获得 IP 的主机，可用 **INFORM**（Message Type=8）仅请求 DNS、网关等参数。服务器回复 ACK（不携带 yiaddr），不分配地址，也不建立租约。

### 3. DHCPv4 报文格式

DHCP 报文由 BOOTP 固定头部、4 字节 magic cookie 和变长 options 组成，固定部分共 **236 字节**：

| 字段 | 长度(字节) | 说明 |
|------|-----------|------|
| **op** | 1 | 报文方向：1=BOOTREQUEST（客户端→服务器），2=BOOTREPLY（服务器→客户端） |
| **htype** | 1 | 硬件类型：1=以太网（Ethernet） |
| **hlen** | 1 | 硬件地址长度：以太网为 6 |
| **hops** | 1 | 客户端置 0，每经过一个中继代理加 1 |
| **xid** | 4 | 事务 ID，随机生成，客户端用它匹配请求与应答 |
| **secs** | 2 | 客户端开始请求后经过的秒数 |
| **flags** | 2 | 仅最高位（B 位，广播标志）有意义：置 1 要求服务器用广播回复 |
| **ciaddr** | 4 | 客户端当前 IP：BOUND 状态下续租、释放时填写 |
| **yiaddr** | 4 | "your" 地址：服务器分配给客户端的 IP，OFFER/ACK 中填写 |
| **siaddr** | 4 | 下一跳服务器 IP：无盘工作站 TFTP 引导等场景使用 |
| **giaddr** | 4 | 中继代理（Relay Agent）的 IP：客户端置 0，见第 6 章 |
| **chaddr** | 16 | 客户端硬件地址（MAC），客户端身份标识的核心 |
| **sname** | 64 | 服务器主机名（可选） |
| **file** | 128 | 启动文件名（可选，无盘引导使用） |
| **magic cookie** | 4 | 固定值 `0x63825363`，标识后续内容为 DHCP 选项 |
| **options** | 变长 | DHCP 选项，见第 5 章 |

> 报文格式直接沿用 BOOTP，DHCP 靠 magic cookie + options 与 BOOTP 区分。客户端通过 **xid + chaddr** 匹配服务器回包。

### 4. 租约管理（T1 / T2 / Renew / Rebind / Release）

DHCPv4 通过租约时间（Lease Time，常见默认 86400 秒即 1 天）与 T1、T2 两个定时器管理地址生命周期：

| 定时器 | 计算 | 触发动作 |
|--------|------|----------|
| **T1** | 0.5 × 租期 | 向**原服务器**单播 REQUEST 续租，进入 RENEWING 状态 |
| **T2** | 0.875 × 租期 | Renew 未收到应答，向**任意服务器**广播 REQUEST 续租，进入 REBINDING 状态 |

续租 REQUEST 携带 Requested IP(50)=当前地址、ciaddr=当前地址及当前租期，服务器确认后续发新租期，客户端重置 T1/T2。

```
BOUND ──T1到期──► RENEWING ──超时──► REBINDING ──超时且租约到期──► INIT
  │                 │                    │
  └──收到ACK────────┘  └──收到ACK────────┘
```

其他租约相关行为：

- **Release（释放）**：客户端主动放弃地址（关机、接口 DOWN），单播发送 RELEASE 报文，服务器把地址收回地址池
- **Decline（拒绝）**：客户端 ARP 检测到地址冲突后发送 DECLINE，服务器将该地址标记为不可用（进入冷却期）
- **租约到期仍未续上**：地址被收回，客户端返回 INIT 重新走四步流程

### 5. 关键 DHCP 选项

选项位于报文尾部，格式为 `选项号(1字节) + 长度(1字节) + 值`。常用选项：

| 选项号 | 选项名 | 作用 |
|--------|--------|------|
| **1** | Subnet Mask | 子网掩码，客户端据此计算本地子网范围 |
| **3** | Router | 默认网关地址列表 |
| **6** | DNS Server | DNS 服务器地址列表 |
| **12** | Hostname | 客户端上报的主机名，便于服务器记录与识别 |
| **15** | Domain Name | 域名后缀，配合主机名完成域名解析 |
| **50** | Requested IP | 客户端请求的特定地址（DISCOVER/REQUEST 中携带） |
| **51** | Lease Time | 租约时长（秒），服务器指定的地址有效时间 |
| **53** | Message Type | 报文类型：1=DISCOVER、2=OFFER、3=REQUEST、4=DECLINE、5=ACK、6=NAK、7=RELEASE、8=INFORM |
| **54** | Server Identifier | 服务器标识（IP 地址），客户端据此选定服务器 |

### 6. DHCP 中继代理（Relay Agent）

DHCP 广播报文**只在本地子网内传播**。客户端与服务器不在同一子网时，需靠中继代理（Relay Agent，通常是网关路由器）转发，实现在**跨子网分配地址**：

1. 客户端广播 DISCOVER 到 `255.255.255.255`，目的端口 67
2. 中继收到后，把报文源 IP 改为自己的接口地址，**giaddr 字段填入中继接口 IP**，hops 加 1，单播转发给服务器（如配置 `ip helper-address` 指向的服务器地址）
3. 服务器依据 **giaddr** 判断客户端所在的子网，从**对应地址池**中分配地址
4. 应答报文经中继回传：中继收到 ACK 后，把目的地址还原为客户端所在子网（可再广播给客户端）

```
客户端 ──DISCOVER(广播)──► 中继路由器 ──DISCOVER(giaddr=中继IP, 单播)──► DHCP服务器
客户端 ◄──ACK(广播)────── 中继路由器 ◄──ACK────────────────────────────── 服务器
```

中继还可在转发时追加 **Relay Agent Information 选项（option 82，RFC 3046）**，携带接入端口、交换机/DSLAM 标识等信息，服务器据此实现**按端口、按用户差异化分配**（不同地址段、不同租期、不同网关）。

> 同一子网内、无中继时，服务器通过 yiaddr/siaddr 与 chaddr 直接回包即可；跨子网场景必须依赖中继填充 giaddr，否则服务器无法判断客户端属于哪个地址池。

### 7. DHCPv4 vs DHCPv6 关键差异

| 对比项 | DHCPv4 | DHCPv6 |
|--------|--------|--------|
| 传输层端口 | UDP：服务器 67，客户端 68 | UDP：服务器 547，客户端 546 |
| 报文数量 | 8 种（DISCOVER/OFFER/REQUEST/ACK/NAK/DECLINE/RELEASE/INFORM） | 13 种（SOLICIT/ADVERTISE/REPLY/...），type 字段区分 |
| 报文类型标识 | 靠 options 中的 Message Type(53) 区分 | 报文头部直接携带 type 字段 |
| 客户端标识 | MAC 地址 + chaddr 字段 | DUID（DHCP Unique Identifier） |
| 地址冲突检测 | 客户端 ACK 后做 ARP 探测，冲突发 DECLINE；服务器也可预先 ping 探测 | 由独立的 DAD（重复地址检测）完成，与 DHCP 解耦 |
| 链路层寻址 | 以**广播**（255.255.255.255）为主，可选单播 | 全部使用**组播**（FF02::1:2）或单播，无广播 |
| 地址获取方式 | 地址与参数绑定分配；仅取参数用 INFORM | 地址与参数分离，有状态/无状态（SLAAC + Information-Request）两种模式 |
| 前缀委派 | 无对应机制 | 支持 PD（前缀代理，IA_PD） |
| 跨链路转发 | 中继代理填 giaddr 后单播转发 | 中继用 Relay-Forward/Relay-Reply 封装（option 9）转发 |

> DHCPv6 的完整笔记见 [m-12-DHCPv6协议.md](07-IPv6%E4%BD%93%E7%B3%BB.md)。
