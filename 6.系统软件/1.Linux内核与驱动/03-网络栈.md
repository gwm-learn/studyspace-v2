# 网络栈


## 内核接收网络包


> 本文配合目录下的 6 张时序/流程示意图，梳理 Linux 内核收包完整路径。核心结论：**收包主要在软中断中批量完成，硬中断只负责"叫醒"**。

### 1. linux网络收包总览

![linux网络收包总览](assets/linux%E7%BD%91%E7%BB%9C%E6%94%B6%E5%8C%85%E6%80%BB%E8%A7%88.png)

收包路径分为五个阶段：

| 阶段 | 位置 | 关键动作 |
|------|------|----------|
| 网卡接收 | 硬件 | DMA 把数据写入内存中的 ring buffer |
| 驱动处理 | 驱动层 | 硬中断触发，驱动置位 NAPI 后退出 |
| 软中断收包 | 内核 | `net_rx_action()` 调用驱动的 `poll()` 批量取包 |
| 协议栈分发 | 内核 | `netif_receive_skb()` 按协议类型分发给 IP/ARP |
| 交付 socket | 内核 | TCP/UDP 按四元组查表，投递到 socket 接收队列 |

数据包在内核中始终以 `struct sk_buff`（skb）为载体，从网卡到 socket 不经过用户空间拷贝（DMA 直达内存）。

### 2. 内核收包路径

![内核收包路径](assets/%E5%86%85%E6%A0%B8%E6%94%B6%E5%8C%85%E8%B7%AF%E5%BE%84.png)

典型收包调用链：

```
网卡 → DMA ring buffer → 硬中断 → net_rx_action（软中断）
  → poll() → napi_gro_receive() → __netif_receive_skb_core()
  → 协议分发 → ip_rcv / arp_rcv → 本机接收或转发
```

硬中断处理函数只做三件事：屏蔽该网卡中断、置位 NAPI、唤醒 `NET_RX_SOFTIRQ` 软中断，然后立刻返回。真正的收包工作全部放到软中断上下文执行，这样能保证硬中断占用 CPU 的时间极短。

### 3. 网卡驱动初始化

![网卡驱动初始化](assets/%E7%BD%91%E5%8D%A1%E9%A9%B1%E5%8A%A8%E5%88%9D%E5%A7%8B%E5%8C%96.png)

驱动 `probe` 阶段完成收包前的准备工作：

1. 分配 **struct net_device** 并注册（`register_netdev`）。
2. 分配 **rx ring buffer**（描述符环），网卡通过 DMA 直接写入，驱动用 `dma_alloc_coherent` 建立映射。
3. 注册 `struct napi_struct`（`netif_napi_add`），绑定驱动自己的 `poll` 收包函数。
4. 注册中断处理函数（如 `igb_msix_ring`），通过 `request_irq` 绑定 IRQ。
5. 注册 `net_device_ops`，包含 `ndo_open`、`ndo_start_xmit` 等回调。

### 4. 启动网卡

![启动网卡](assets/%E5%90%AF%E5%8A%A8%E7%BD%91%E5%8D%A1.png)

`ip link set eth0 up` 触发 `ndo_open()`：

1. 分配并初始化 rx 描述符，把接收缓冲区的 DMA 地址写入描述符。
2. 使能 NAPI（`napi_enable`），软中断才会调度该网卡的 poll。
3. 写网卡寄存器使能接收队列、开中断。
4. 调用 `netif_carrier_on` 通知协议栈链路可用，注册 `netif_receive_skb` 分发所需信息。

注意顺序：**先填好接收缓冲、再开中断**。如果先开中断，网卡立刻收到数据写不进 buffer 会出错。

### 5. tcpdump工作

![tcpdump工作](assets/tcpdump%E5%B7%A5%E4%BD%9C.png)

tcpdump 通过 **AF_PACKET 原始套接字**旁路抓包，`packet_type` 机制实现：

- 内核维护一个 `ptype_all`（所有包）和 `ptype_base`（按协议）链表，AF_PACKET socket 会把自己挂到 `ptype_all` 上。
- `__netif_receive_skb_core()` 在分发前先遍历 `ptype_all`，把 skb 复制（`skb_clone`）一份给 tcpdump。
- 这就是为什么 tcpdump 能抓到**所有**协议栈收发的包，包括被防火墙丢弃的包。抓包接口使用 `PACKET_MR_PROMISC` 时还会让网卡进入混杂模式。

### 6. 软中断处理

![软中断处理](assets/%E8%BD%AF%E4%B8%AD%E6%96%AD%E5%A4%84%E7%90%86.png)

`net_rx_action()` 是收包软中断的核心函数，执行逻辑：

1. 从 per-CPU 的 `softnet_data->poll_list` 取出被唤醒的 NAPI 实例。
2. 循环调用每个实例的 `poll()`，驱动在 poll 中从 ring buffer 批量取包。
3. 每轮有 **budget 额度**（默认 300）和时间限制，防止软中断长期霸占 CPU。
4. 包在 poll 内经 `napi_gro_receive()`（GRO 合并小包）后交给 `netif_receive_skb()` 进入协议栈。
5. 若预算耗尽但仍有包未处理，重新置位 NAPI，软中断会在下一轮继续。

**NAPI 的核心思想**：用轮询代替每包一次中断，高流量下极大降低 CPU 开销，是网卡驱动性能的关键。

### 总结

收包路径的性能关键点：DMA 零拷贝、NAPI 批量轮询、GRO 合并小包、budget 防饿死。排查丢包时按此路径分段检查：ring buffer 是否溢出（`ethtool -S` 看 rx_dropped）、NAPI 是否频繁退出、软中断 CPU 占用是否过高。

## 内核与用户进程协作


> 本文配合目录下的 9 张示意图，梳理 socket 内核结构与 epoll 事件通知机制，重点回答"数据从内核到用户进程怎么交付、epoll 为什么高效"。

### 1. socket 内核结构

![socket 内核结构](assets/socket%E5%86%85%E6%A0%B8%E7%BB%93%E6%9E%84.png)

内核中一个 socket 由多层结构组成：

| 结构 | 作用 |
|------|------|
| `struct socket` | BSD socket 抽象层，用户 `fd` 与之对应，包含 `file` 引用 |
| `struct sock` | 协议相关的通用 socket 结构，管理发送/接收队列、等待队列、拥塞状态 |
| `struct proto` | 协议操作集，TCP 为 `tcp_prot`（`tcp_sendmsg`/`tcp_recvmsg`），UDP 为 `udp_prot` |
| `struct file` | VFS 文件对象，`fd -> file -> socket` 形成完整链路 |

用户持有的 `fd` 最终通过 `fdget()` 找到 `struct file`，再找到 `socket` 和 `sock`，这就是 `read/write/recv/send` 都能操作 socket 的原因。

### 2. 同步阻塞的网络IO

![同步阻塞的网络IO](assets/%E5%90%8C%E6%AD%A5%E9%98%BB%E5%A1%9E%E7%9A%84%E7%BD%91%E7%BB%9CIO.png)

同步阻塞模型是最简单的 IO 模型：

1. 进程调用 `recvfrom()`，内核发现 socket 接收队列为空。
2. 进程被挂到 socket 的 **等待队列**（`sk_sleep`/`wq`）上，状态置为 `TASK_INTERRUPTIBLE`，主动让出 CPU。
3. 数据到达后，内核把数据放入接收队列并唤醒等待进程。
4. 进程被调度回来，从接收队列拷贝数据到用户缓冲区，`recvfrom()` 返回。

特点是实现简单、每连接一个线程，并发量大时线程开销是瓶颈，因此才有 epoll 等 IO 多路复用方案。

### 3. recvfrom阻塞

![recvfrom阻塞](assets/recvfrom%E9%98%BB%E5%A1%9E.png)

阻塞细节展开：

- 用户调用 `recvfrom()` → `sock_recvmsg()` → `tcp_recvmsg()`。
- `tcp_recvmsg()` 循环检查接收队列，为空且非 MSG_DONTWAIT 时调用 `sk_wait_data()` 睡眠。
- 唤醒后检查 `sk_err`（出错立即返回）、`sk_shutdown`（对端关闭返回 0）。
- 有数据则用 `skb_copy_datagram_iter()` 把数据从 skb 拷贝到用户空间 iovec。

**关键点**：TCP 收数据是"按字节流"语义，一次 recv 可能只取出队列里 skb 的部分数据，剩余的留在队列供下次读取。

### 4. 软中断模块

![软中断模块](assets/%E8%BD%AF%E4%B8%AD%E6%96%AD%E6%A8%A1%E5%9D%97.png)

数据到达的唤醒路径由软中断完成：

```
网卡硬中断 → NET_RX_SOFTIRQ 软中断 → 驱动 poll → 协议栈 → tcp_v4_rcv
  → 四元组查 sock → 放入接收队列 sk_receive_queue
  → sk_data_ready() 回调 → 唤醒在等待队列上睡眠的进程
```

软中断里完成"入队 + 唤醒"，进程被唤醒后再在**进程上下文**完成拷贝。内核刻意把"收包入队"和"用户拷贝"分开，拷贝不占用软中断时间。

### 5. eventpoll对象

![eventpoll对象](assets/eventpoll%E5%AF%B9%E8%B1%A1.png)

`epoll_create()` 创建 `struct eventpoll`，核心成员：

- **rbr**：红黑树，存放所有被监控的 epoll 项，增删改查复杂度 O(log n)。
- **rdllist**：就绪链表，保存当前有事件发生的 epoll 项，`epoll_wait` 直接拷贝这个链表。
- **wq**：等待队列，`epoll_wait` 无事件时睡眠在此。
- **ovflist**：事件溢出的暂存队列，防止就绪链表被锁占用过久。

红黑树负责"管理监控对象"，就绪链表负责"快速取出有事件的对象"，两者配合是 epoll 高效的基础。

### 6. epoll添加socket

![epoll添加socket](assets/epoll%E6%B7%BB%E5%8A%A0socket.png)

`epoll_ctl(EPOLL_CTL_ADD)` 把 socket 加入监控：

1. 查找红黑树确认该 fd 尚未注册。
2. 创建 `struct epitem`，并生成 `struct eppoll_entry`。
3. 调用 `ep_ptable_queue_proc()`，把 epoll 的回调 `ep_poll_callback` 挂到 socket 的等待队列上。
4. 如果该 socket 此刻已有事件，直接加入就绪链表。

核心思想：**回调提前挂载**。socket 有事件时由协议栈直接调用 `ep_poll_callback`，无需 epoll_wait 时再逐个扫描。

### 7. epollwait原理

![epollwait原理](assets/epollwait%E5%8E%9F%E7%90%86.png)

`epoll_wait()` 的流程：

1. 检查就绪链表 `rdllist` 是否为空。
2. 为空则当前进程挂到 `eventpoll->wq` 睡眠（可设超时）。
3. 任一被监控 socket 有事件 → 回调 `ep_poll_callback` 把对应 epitem 挂入就绪链表，并唤醒 `wq` 上的进程。
4. 进程醒来后遍历就绪链表，把事件（fd + events）拷贝到用户传入的 `epoll_event` 数组。
5. 若使用 `EPOLLET`（边沿触发），拷贝后该 epitem 从就绪链表移除，下次事件需重新触发。

### 8. epoll相关队列

![epoll相关队列](assets/epoll%E7%9B%B8%E5%85%B3%E9%98%9F%E5%88%97.png)

epoll 涉及三类队列，理解它们就理解了 epoll：

| 队列 | 所属 | 作用 |
|------|------|------|
| socket 等待队列 | 每个 sock | 挂载 epoll 回调 `ep_poll_callback` |
| 就绪链表 rdllist | eventpoll | 存放有事件的 epitem，epoll_wait 直接读取 |
| 睡眠等待队列 wq | eventpoll | epoll_wait 进程无事件时睡眠在此 |

数据到达时链式触发：协议栈唤醒 socket 队列上的回调 → 回调挂入 rdllist → 唤醒 wq 上的 epoll_wait 进程。

### 9. epoll原理

![epoll原理](assets/epoll%E5%8E%9F%E7%90%86.png)

综合全貌：

- **水平触发（LT，默认）**：只要 socket 缓冲区还有数据，每次 epoll_wait 都会返回该 fd，不容易漏事件。
- **边沿触发（ET）**：仅在状态变化（无→有数据）时通知一次，要求用户一次性把数据读完，否则可能饥饿。
- epoll 相比 select/poll 的优势：监控对象用红黑树管理（O(log n)），就绪对象直接拿到（O(1)），且通过回调机制避免了全量扫描，所以支持几十万连接的场景。

### 总结

sendmsg/recvmsg 本质是"用户空间与 socket 缓冲区之间的数据搬运"，epoll 则负责高效地告诉进程"哪个 socket 可以搬了"。理解这三层（socket 结构、数据路径、事件通知）就能覆盖绝大多数网络编程的底层问题。

## 内核发送网络包


> 本文配合目录下的 12 张示意图，梳理 Linux 内核发送网络包完整路径：从用户空间 socket 写入，经传输层、网络层、邻居子系统、流量控制（Qdisc），最后由驱动写入网卡。

### 1. 内核发送网络包

![内核发送网络包](assets/%E5%86%85%E6%A0%B8%E5%8F%91%E9%80%81%E7%BD%91%E7%BB%9C%E5%8C%85.png)

发送总览路径：

```
用户进程 → send() → socket 层 → 传输层(TCP/UDP) → 网络层(路由+OUTPUT链)
  → 邻居子系统(ARP/NDP) → dev_queue_xmit → Qdisc(tc egress)
  → ndo_start_xmit → DMA ring buffer → 网卡硬件
```

发送与接收最大的区别：发送在**进程上下文**启动，可能被拥塞控制、Qdisc 队列满等原因阻塞（异步或同步等待）。

### 2. 网络发送过程

![网络发送过程](assets/%E7%BD%91%E7%BB%9C%E5%8F%91%E9%80%81%E8%BF%87%E7%A8%8B.png)

核心原则是**减少拷贝**：用户数据先拷贝到内核 skb（`send` 阶段唯一一次拷贝），后续各层只修改 skb 的头部指针，不搬数据。skb 通过预留的头部空间（`skb_reserve`）逐层"回头"填各层头部：TCP 头、IP 头、以太网头都填在同一块内存上。

### 3. 发送队列

![发送队列](assets/%E5%8F%91%E9%80%81%E9%98%9F%E5%88%97.png)

- **TCP 发送队列**（`sk_write_queue`）：已发送未确认的数据段，等待 ACK 后释放，是 TCP 重传的基础。
- **socket 写队列**：用户已写入但尚未发送的 skb。
- **Qdisc 队列**：设备层的排队规则，位于协议栈与驱动之间。

队列是连接"用户写入速度"与"网络发送速度"的缓冲，队列满时触发背压（backpressure）：TCP 会停止发送窗口增长，UDP 则直接丢包或返回 ENOBUFS。

### 4. send系统调用

![send系统调用](assets/send%E7%B3%BB%E7%BB%9F%E8%B0%83%E7%94%A8.png)

`send()` 系统调用路径：

1. `__sys_sendto()` 通过 fd 找到 `struct socket`。
2. `sock_sendmsg()` → `sock->ops->sendmsg()`，TCP 走 `tcp_sendmsg()`。
3. `tcp_sendmsg()` 把用户缓冲区的数据拷入 skb（`skb_copy_to_page_nocache`），满 MSS 后交给 `tcp_write_xmit()`。
4. `tcp_write_xmit()` 按发送窗口和拥塞窗口决定发多少，调用 `ip_queue_xmit()` 进入网络层。

注意 `send()` 返回并不代表数据已到网卡，只代表数据已进入内核发送队列。

### 5. 传输层拷贝

![传输层拷贝](assets/%E4%BC%A0%E8%BE%93%E5%B1%82%E6%8B%B7%E8%B4%9D.png)

传输层拷贝发生在 `sendmsg` 阶段：

- 内核为 skb 分配数据页（`alloc_skb_with_frags`），把用户数据**从用户空间拷入内核内存页**。
- 大数据量用 **MSG_ZEROCOPY** 时，用户内存页通过 pin 直接映射进 skb，避免拷贝，内核需要时再发通知回收。
- 拷贝完成后 `skb->len` 增加，传输层（尤其 TCP）按窗口和 MSS 组织发送。

### 6. 传输层发送

![传输层发送](assets/%E4%BC%A0%E8%BE%93%E5%B1%82%E5%8F%91%E9%80%81.png)

TCP 发送入口 `tcp_write_xmit()`：

1. 检查拥塞窗口 `cwnd` 与发送窗口 `snd_wnd`，能发多少发多少。
2. 为每个 skb 计算并填充 TCP 头：序号（seq）、确认号（ack）、标志位、校验和。
3. 开启 **TSO/GSO**（TCP 分段卸载）时，大包在驱动/网卡处分段，减轻 CPU 负担。
4. 通过 `ip_queue_xmit()` 交给 IP 层，同时注册重传定时器。

### 7. 网络层发送

![网络层发送](assets/%E7%BD%91%E7%BB%9C%E5%B1%82%E5%8F%91%E9%80%81.png)

`ip_queue_xmit()` 到 `ip_output()`：

1. 查路由（`ip_route_output_flow`）确定出口设备和下一跳。
2. 经过 Netfilter **OUTPUT 链**（`NF_INET_LOCAL_OUT` 钩子），执行 SNAT、防火墙、mangle 等规则。
3. `ip_finish_output()` 处理分片（超过 MTU 且不允许分片则返回 EMSGSIZE）。
4. 进入 `ip_finish_output2()`，调用邻居子系统解析二层信息。

### 8. 邻居子系统

![邻居子系统](assets/%E9%82%BB%E5%B1%85%E5%AD%90%E7%B3%BB%E7%BB%9F.png)

邻居子系统负责"把三层下一跳解析成二层 MAC"：

- `ip_finish_output2()` → `neigh_output()` → `neigh_resolve_output()`。
- 邻居表（`struct neighbour`）有状态机：`NUD_NONE → NUD_INCOMPLETE（发ARP请求）→ NUD_REACHABLE → NUD_STALE`。
- 缓存命中（REACHABLE）直接填以太网头；未命中则发出 **ARP 请求**，skb 挂到邻居的队列等待应答，解析成功后补发。
- IPv6 使用 NDP（Neighbor Discovery Protocol）完成同样的工作。

### 9. 网络设备子系统

![网络设备子系统](assets/%E7%BD%91%E7%BB%9C%E8%AE%BE%E5%A4%87%E5%AD%90%E7%B3%BB%E7%BB%9F.png)

邻居解析完成后调用 `dev_queue_xmit()`：

1. 检查设备是否 UP、是否回环，判断是直接发送还是排队。
2. 调用 `__dev_xmit_skb()` 进入设备的 **Qdisc**。
3. 对于回环/虚拟设备（如 veth）可能直接调用 `ndo_start_xmit` 送入对端。

`struct net_device_ops` 中的 `ndo_start_xmit` 是协议栈调用驱动的唯一出口。

### 10. 软中断调度

![软中断调度](assets/%E8%BD%AF%E4%B8%AD%E6%96%AD%E8%B0%83%E5%BA%A6.png)

发送完成的中断在软中断中处理：

- 网卡发送完成后触发硬中断，唤醒 `NET_TX_SOFTIRQ` 软中断。
- 软中断处理 `net_tx_action()`，调用驱动的发送完成处理函数。
- 驱动回收已发送的 skb 与 DMA 映射（`dev_kfree_skb_any`），释放内存，更新统计。

### 11. igb网卡驱动发送

![igb网卡驱动发送](assets/igb%E7%BD%91%E5%8D%A1%E9%A9%B1%E5%8A%A8%E5%8F%91%E9%80%81.png)

igb（Intel 千兆）驱动发送流程：

1. Qdisc 调度出 skb → `igb_xmit_frame()`。
2. 检查发送队列是否有空描述符，没有则返回 `NETDEV_TX_BUSY`。
3. 用 `skb_dma_map` 建立 DMA 映射，把数据地址写入 **tx ring buffer** 描述符。
4. 写网卡寄存器（`E1000_TDT`）通知硬件"有新数据可发"。
5. 若开启 TSO，网卡硬件负责 TCP 分段，CPU 只提交一个大数据段。

### 12. ringbuffer内存回收

![ringbuffer内存回收](assets/ringbuffer%E5%86%85%E5%AD%98%E5%9B%9E%E6%94%B6.png)

发送完成的回收机制：

- 网卡通过中断告知"描述符 N 已发送完成"。
- 驱动记录已回收位置（`next_to_clean`），把 skb 释放、DMA 映射解除。
- ring buffer 的可用描述符数 = 已回收位置 - 已提交位置，**回收不及时会导致发送队列满**（`NETDEV_TX_BUSY`），影响吞吐。
- 常见问题：中断合并（interrupt coalescing）延迟回收、驱动 bug 导致描述符泄漏，都会表现为"缓存下不去"。

### 总结

发送路径的性能要点：单次拷贝（send 阶段）、TSO/GSO 硬件分段卸载、Qdisc 队列管理、DMA ring buffer 及时回收。排查发送丢包：`ip -s link` 看 tx_errors、`tc -s qdisc` 看队列 drop、`ethtool -S` 看硬件统计。

## Linux 内核收发包流程


## 概述

数据包在内核中的路径分为两条：**收包路径（RX）**和**发包路径（TX）**。收包从网卡硬件收到数据开始，经过驱动、中断/软中断、协议栈，最终交给用户空间 socket；发包则反向，从用户空间 socket 开始，经过传输层、网络层、邻居子系统、流量控制（Qdisc）和驱动，最终写入网卡硬件。

两条路径以**网卡驱动**为分界：驱动以下是与硬件打交道的收发包，驱动以上是内核协议栈的处理。中间通过 `struct sk_buff`（skb）这个核心数据结构承载数据，每个包在内核中就是一个 skb。# 收包路径

### 1. 网卡驱动收包

网卡收到数据后通过 DMA 把数据写入内存中的**环形缓冲区（ring buffer）**，然后产生硬中断通知 CPU。驱动在中断处理函数 `xxx_rx()` 中读取 ring buffer 中已就绪的描述符，通过 `napi_gro_receive()` 或 `netif_receive_skb()` 把数据交给协议栈。

- **DMA 环形缓冲区**：驱动初始化时分配，网卡直接写入，减少拷贝。
- **NAPI**：驱动注册 `struct napi_struct`，通过 `poll()` 批量收包，避免每个包都触发一次硬中断。
- **GRO（Generic Receive Offload）**：`napi_gro_receive()` 先把多个小包合并成一个大包再上交，减少协议栈处理次数。

### 2. NAPI 软中断

收包处理主要在**软中断（softirq）**中执行，流程如下：

1. 网卡硬中断 → 驱动中断处理函数：屏蔽中断、置位 NAPI、唤醒 `NET_RX_SOFTIRQ` 软中断。
2. 软中断核心 `net_rx_action()` 遍历被唤醒的 NAPI 实例列表，逐个调用驱动的 `poll()`。
3. `poll()` 循环从 ring buffer 取包（`GRO` 合并后），调用 `napi_gro_receive()` → `__netif_receive_skb()` → `netif_receive_skb()`，把 skb 送入协议栈。
4. 每轮 `poll()` 有 `budget`（默认 300）额度限制，防止软中断饿死其他任务；取完或额度耗尽后退出，必要时重新触发。硬中断处理时间被压到最短，这是 NAPI 的设计核心。

### 3. netif_receive_skb 与协议栈分发

`netif_receive_skb()`（实际是 `__netif_receive_skb_core()`）是收包进入协议栈的入口，它做的事：

1. 处理 **tc ingress** 挂载点，即 `tc filter` 的 ingress 方向规则。
2. 经过 **Netfilter** 的 `PREROUTING` 钩子（`nf_hook`），实现 DNAT、防火墙、桥接过滤等。
3. 判断包类型（`skb->protocol`）并交给对应的 `packet_type` 处理函数：IP 包进入 `ip_rcv()`，ARP 进入 `arp_rcv()`，也支持原始套接字（AF_PACKET）。

### 4. IP 层处理

`ip_rcv()` 开始 IP 层处理，核心路径：

- 检查版本、校验和、长度等合法性。
- `ip_rcv_finish()` 调用 `ip_route_input_noref()` 路由查找，决定是**本机接收**还是**转发**：
  - 本机接收：进入 `ip_local_deliver()`，经 `NF_INET_LOCAL_IN` 钩子后按协议分发。
  - 转发：进入 `ip_forward()`，经 `NF_INET_FORWARD` 钩子，然后走 `ip_output()`（发送路径）。
- 开启 **iptables** 时，`mangle`/`nat`/`filter` 表挂在上述各钩子上执行规则匹配。

### 5. 传输层分发到 socket

本机接收的包进入 `ip_local_deliver()` 后，根据 `skb->protocol`（`IPPROTO_TCP` / `IPPROTO_UDP` / `IPPROTO_ICMP`）交给传输层：

- **TCP**：`tcp_v4_rcv()`，通过 4 元组（源/目的 IP、源/目的端口）查找连接，送入对应 socket 的接收队列，触发 `epoll`/`select` 唤醒等待进程。
- **UDP**：`udp_rcv()`，通过 4 元组查 UDP socket 哈希表，投递到 socket 接收缓冲区。
- **ICMP**：`icmp_rcv()`，处理 ping 等，或上报错误。

传输层到 socket 的交付依赖 **socket 哈希表**（如 TCP 的 `ehash`、UDP 的 `udp_table`）。用户空间进程最终通过 `recvmsg()`/`read()` 从 socket 缓冲区取走数据，收包路径结束。

收包总览：

```
网卡 → DMA ring buffer → 硬中断 → NAPI 软中断 → netif_receive_skb → PREROUTING → 路由
  → 本机: ip_local_deliver → LOCAL_IN → TCP/UDP → socket
  → 转发: ip_forward → FORWARD → ip_output（进入发送路径）
```

## 发送路径

### 1. socket 到传输层

用户进程调用 `send()`/`write()` 把数据写入 socket。socket 层把数据封装成 skb 后调用传输层发送接口：

- **TCP**：`tcp_sendmsg()` → `tcp_write_xmit()`，按拥塞窗口发送，通过 `ip_queue_xmit()` 交给 IP 层。
- **UDP**：`udp_sendmsg()` → `ip_append_data()` / `ip_push_pending_frames()`，构造好 UDP 头后调用 `ip_local_out()`。
- 此处同时完成端口、校验和、分段（TCP 分段由发送侧完成）等封装，发送路径由此开始。

### 2. 传输层到 IP 层

IP 层发送核心是 `ip_output()` 及 `ip_finish_output()`：

- 查路由确定**出口设备**和下一跳（`ip_route_output_flow()`）。
- 经过 Netfilter `NF_INET_LOCAL_OUT` 钩子，执行 OUTPUT 链（如 NAT 的 SNAT、防火墙）。
- `ip_finish_output()` 调用 `ip_finish_output2()`，通过 **邻居子系统** 解析二层信息。

### 3. 邻居子系统

`ip_finish_output2()` 调用邻居子系统（`neigh_output()` / `neigh_resolve_output()`）：

- 通过 ARP（IPv4）或 NDP（IPv6）解析下一跳的 **MAC 地址**，填充以太网头。
- 若邻居条目已缓存，直接构造二层头；未缓存则发出 ARP 请求，skb 挂起等待应答。
- 邻居解析完成后调用 `dev_queue_xmit()` 进入流量控制层。

### 4. Qdisc 排队

`dev_queue_xmit()` 是流量控制的入口，把 skb 送入出口设备的**排队规则（Qdisc）**：

- 默认 `pfifo_fast` 按优先级入队，OpenWrt 上常用 `htb`、`fq_codel` 实现限速与公平调度。
- 队列满时触发拥塞控制（如 TCP 背压），否则调度器按规则取包，调用驱动的发送函数。
- 这里对应 **tc egress** 方向，即 `tc filter` 的出口规则。

### 5. 驱动发送

Qdisc 取出 skb 后调用 `ndo_start_xmit()`（驱动注册的 `net_device_ops` 发送方法）：

- 驱动把 skb 数据通过 DMA 映射到 ring buffer，通知网卡硬件发送。
- 若 ring buffer 已满，返回 `NETDEV_TX_BUSY`，Qdisc 稍后重试。
- 发送完成后硬中断确认，回收 skb 与 DMA 映射（NAPI 的 poll 里顺便处理发送完成队列）。

发送总览：

```
socket → TCP/UDP → IP 层（路由 + OUTPUT 链）→ 邻居子系统（ARP/NDP）
  → dev_queue_xmit → Qdisc（tc egress）→ ndo_start_xmit → DMA → 网卡
```

## 软中断与硬中断小结

| 项目 | 硬中断（hardirq） | 软中断（softirq） |
|------|-------------------|-------------------|
| 触发 | 网卡收到/发完数据 | 硬中断处理中 `raise_softirq` 触发 |
| 处理 | 收包：置位 NAPI；发包：回收 skb | 收包：`net_rx_action()` 轮询 NAPI；发包：发送完成处理 |
| 特点 | 快进快出，不能长时间占用 | 可被打断，受 budget 限制 |
| 关闭 | 不可被中断 | 可被硬中断打断 |

理解收发包流程是分析 OpenWrt 网络问题的前提：丢包可能在驱动 ring buffer、NAPI budget、Netfilter 钩子、Qdisc 队列或 socket 缓冲区任一环节发生，排查时按路径逐段定位。

## Linux 网络命名空间（Network Namespace）


### 概述

网络命名空间是 Linux 提供的一种内核级隔离机制，属于 `struct nsproxy` 维护的命名空间族之一。每个网络命名空间拥有**独立**的网络协议栈实例，包括自己的网络设备、IP 地址、路由表、防火墙（Netfilter）规则、socket 以及 `/proc/net` 等网络资源。不同命名空间之间的网络默认完全隔离，必须通过 **veth 对**、**网桥**或**macvlan** 等虚拟设备显式打通才能通信。

命名空间在用户空间通过 `clone()` 系统调用（`CLONE_NEWNET` 标志）或 `unshare()` 创建，最终由 `netns` 子系统（`net/core/net_namespace.c`）管理，每个命名空间对应内核中的一个 `struct net` 实例。

### 核心隔离资源

| 资源 | 说明 |
|------|------|
| 网络设备 | 每个 netns 有独立的设备列表，物理设备默认属于初始命名空间，veth/macvlan/网桥等虚拟设备可移动 |
| 路由表 | 每个 netns 有独立的路由表（main/local 等），路由互不影响 |
| Netfilter | iptables/nftables 规则按 netns 隔离，每个 netns 拥有自己的表与链 |
| 网络协议栈 | TCP/IP 协议栈、socket 哈希表、ARP/邻居表均独立 |
| 系统参数 | `/proc/sys/net/*` 下的参数（如 `ip_forward`）按 netns 独立配置 |
| socket | 每个 netns 有独立的 socket 表和端口空间，监听端口互不冲突 |

### 关键虚拟设备

- **veth（Virtual Ethernet）**：成对出现的虚拟网卡，数据从一端进入必然从另一端流出，是打通两个 netns 的最常用手段。
- **Linux Bridge**：相当于软件交换机，可以把多个 veth 设备桥接在一起，实现多个 netns 互通。
- **macvlan / ipvlan**：把物理网卡虚拟出多个带不同 MAC/IP 的接口，常用于多 WAN 或容器场景。

### OpenWrt 中的 netns 应用

#### 1. 业务服务隔离

OpenWrt 上某些关键业务（如 DNS 服务、上网行为管理、dnsmasq）可以放进独立命名空间运行，与主路由进程隔离：

- 服务进程只见自己的网络视图，不干扰主命名空间的路由与防火墙配置。
- 即使业务异常（如大量占用端口、崩溃），也不会波及宿主协议栈。
- 结合 cgroups 可实现更完整的进程级隔离。

#### 2. 多 WAN / 多运营商隔离

每个 WAN 连接可以放入独立的命名空间，各自拥有独立的路由表和默认路由：

- 各运营商的路由策略互不干扰，策略路由（ip rule）按命名空间划分，避免路由冲突。
- 配合 veth 和策略路由实现**端口分流**或**应用分流**：按源 IP、目标 IP 或应用特征把流量导向不同 WAN。
- 每个 netns 可独立配置自己的 DNS、防火墙和连接跟踪（conntrack）表。

#### 3. 测试与研发环境

在 OpenWrt 开发板上用 `ip netns` 快速搭建隔离测试环境，验证路由、NAT、防火墙改动，不影响实际业务命名空间。

### ip netns 命令

```shell
ip netns add ns1                      # 创建命名空间 ns1
ip netns list                         # 列出所有命名空间
ip netns delete ns1                   # 删除命名空间

ip netns exec ns1 bash                # 进入 ns1 并执行命令
ip netns exec ns1 ip addr             # 查看 ns1 的网卡与地址

# 创建 veth 对并分别放入两个命名空间
ip link add veth0 type veth peer name veth1
ip link set veth0 netns ns1
ip link set veth1 netns ns2

# 在 ns1 内配置地址并启用
ip netns exec ns1 ip addr add 10.0.0.1/24 dev veth0
ip netns exec ns1 ip link set veth0 up
```

| 常用子命令 | 作用 |
|-----------|------|
| `add/delete` | 创建/删除命名空间 |
| `exec` | 在指定命名空间中执行命令 |
| `list` | 列出全部命名空间 |
| `monitor` | 监控命名空间创建删除事件 |

### 小结

网络命名空间是 OpenWrt 实现多 WAN 隔离、业务容器化的基础能力。排查命名空间相关问题时，先确认进程运行在哪个 netns（`ip netns identify <pid>`），再检查该 netns 内的路由表、防火墙与网络设备是否配置正确，通常能快速定位隔离导致的"看不见"问题。

## netlink 通信机制


## 概述

netlink 是 Linux 内核与用户空间通信的**双向异步套接字机制**，内核侧由 `net/netlink/` 实现，用户空间以 `AF_NETLINK` 套接字访问。相比 ioctl，netlink 支持多播、异步、增量变更，是内核网络子系统对外的事实标准接口。OpenWrt 中 `ip`、`iw`、`nft`、`ubus`（部分）等工具都通过 netlink 与内核交互。

## netlink 基础机制

### 1. 套接字与协议族

用户空间用 `socket(AF_NETLINK, SOCK_RAW, <协议>)` 创建，内核侧对应 `struct netlink_sock`。协议号决定语义，常见有：

- `NETLINK_ROUTE`（0）：路由、邻居、地址等网络配置（rtnetlink）。
- `NETLINK_GENERIC`（16）：通用协议（generic netlink），动态分配子协议。
- `NETLINK_NETFILTER`（12）：nftables、iptables 规则下发。

### 2. 消息格式

netlink 消息是带对齐的二进制帧，所有协议共用同一封装：

```
struct nlmsghdr { 长度; 类型; 标志; 序号; 进程/组 ID; }
    + payload（按协议定义，rtnetlink 多为 ifinfomsg/rtmsg）
```

- **标志位**：`NLM_F_REQUEST`（请求）、`NLM_F_ACK`（要求应答）、`NLM_F_DUMP`（枚举全部）、`NLM_F_CREATE`/`NLM_F_EXCL`（新建/排他）。
- **序号**：请求与应答配对，异步场景靠它关联。
- 多消息用 `NLMSG_DONE` 或 `NLMSG_ERROR` 结束批量返回。

### 3. 单播与多播

- **单播**：用户主动查询/配置，内核应答；`ip addr add`、`nft add rule` 走此路径。
- **多播**：内核主动广播事件，用户订阅 `bind()` 到组（`RTMGRP_*`）。路由变化、链路 up/down 通过多播通知，`ip monitor` 就是订阅组。

## generic netlink

`NETLINK_GENERIC`（genl）解决协议号耗尽与消息复用问题：**一个套接字承载多个子系统**，用字符串族名区分：

- 用户发 `CTRL_CMD_GETFAMILY` 查族 ID，内核动态分配 `family id`。
- 每个族定义自己的 **命令 + 属性（attribute）**，属性用 `nla_type`（TLV 编码）组织，可扩展、可嵌套。
- 内核侧 `genl_family` 注册表，用户侧用 `genlmsg_put()` / `genlmsg_multicast()` 构造消息。

典型例子：

- **nftables**：`nft` 通过 genl 下发规则，族名 `nftables`。
- **nl80211**：`iw`、hostapd 通过 genl 控制 WiFi，族名 `nl80211`。
- **wireguard**：wg 配置走 genl，族名 `wireguard`。
- **ubus**（OpenWrt）对外也有 netlink 后端（`ubusd` 本身是 unix socket，但部分交互走 netlink）。

## rtnetlink

rtnetlink 是 `NETLINK_ROUTE` 上的**网络配置协议**，`iproute2` 全家（`ip`、`tc`）的基础：

- 消息类型 `RTM_*`：`RTM_NEWLINK`/`RTM_DELLINK`（链路）、`RTM_NEWADDR`/`RTM_DELADDR`（地址）、`RTM_NEWROUTE`/`RTM_DELROUTE`（路由）、`RTM_NEWNEIGH`（邻居/FDB）。
- payload 以 `ifinfomsg` / `ifaddrmsg` / `rtmsg` 开头，后跟 `rtattr` 属性（`IFLA_*`、`IFA_*`、`RTA_*`）。
- OpenWrt 中 **netifd** 通过 rtnetlink 创建/配置接口（`br-lan`、VLAN、地址），`ubus call network.interface dump` 查到的数据最终来自内核 rtnetlink 状态。
- 事件多播：链路状态变化（`RTM_NEWLINK`）广播给订阅者，`ip monitor link` 可见。

## 与 ioctl / sysfs 对比

| 维度 | netlink | ioctl | sysfs |
|------|---------|-------|-------|
| 通道 | socket（`AF_NETLINK`） | 设备 fd + 命令码 | 虚拟文件系统 |
| 方向 | 双向、异步、支持多播 | 单向同步请求-应答 | 单向属性读写 |
| 事件 | 内核主动推送 | 不支持 | 无（靠 poll/uevent） |
| 扩展 | 属性 TLV，易增字段 | 命令码有限，难扩展 | 一个属性一个文件 |
| 典型场景 | 网络配置、路由、规则 | 老式驱动控制、pppd | 设备属性、电源管理 |

ioctl 适合**简单同步控制**（如 pppd 的 `PPPIOC*`、老驱动私有命令），但命令码是全局共享的整数空间，增字段不兼容；sysfs 适合**暴露只读属性**（`/sys/class/net/*/`），写路径受限；netlink 以协议化消息替代，动态扩展且支持事件，是现代内核首选的配置通道。

## 调试要点

- `strace -e socket,sendmsg,recvmsg ip link`：观察 ip 工具发出的 netlink 消息。
- `ip monitor`：订阅多播组看内核事件流。
- 抓包：`tcpdump -i lo 'port 0'` 看不到 netlink，需 `strace` 或内核 `netlink` tracepoint（`tracefs`）。
- 内核侧出错会在应答里带 `NLMSG_ERROR` 和 `errno`，用户工具如 `ip` 会直接打印错误原因。
