# 代码质量与测试

> 解决什么问题：让 bug 在提交前暴露、让代码可维护、让改动不破坏旧功能。
> 不解决：具体测试环境/产测（见 [测试方法](../../10.工程方法/5.测试与实验/01-测试方法.md)）。

## 1. 代码质量维度

| 维度 | 要点 |
|---|---|
| 正确性 | 边界/失败路径/并发 |
| 可读性 | 命名/结构/注释 |
| 可维护性 | 模块化/低耦合 |
| 可测试性 | 依赖注入/纯函数 |
| 可移植性 | 字节序/对齐/类型宽度 |
| 安全性 | 输入校验/权限/密钥 |

## 2. 命名与结构

- 名字表达意图：`retry_count` 而不是 `n`。
- 函数短小，只做一件事。
- 参数少（≤3–4），多用结构体。
- 避免全局状态；必须有时写明生命周期/锁。
- 错误处理统一（返回码/errno/异常，三选一）。

## 3. 错误处理

| 方式 | 适用 |
|---|---|
| 返回码 | C/嵌入式 |
| errno | 系统调用 |
| 异常 | C++/可控环境 |
| `expected/Result` | 现代 C++/Rust |
| 断言 | 不可恢复的内部错误 |

规则：

- 不吞错；失败要记录上下文。
- 失败路径也要释放资源（goto cleanup/RAII）。
- 区分“可恢复/不可恢复”。
- 日志不打印密钥/口令。

## 4. 测试金字塔

```text
        E2E/系统（少）
     集成/接口（中）
   单元测试（多）
```

| 层 | 目标 | 工具 |
|---|---|---|
| 单元 | 函数/模块 | Unity/CUnit/gtest/pytest |
| 集成 | 模块协作 | 脚本/容器 |
| 系统 | 整机 | 板卡/机器人 |
| 性能 | 吞吐/时延 | iperf3/trex |
| 稳定 | 长时间 | soak/老化 |

单元测试要点：

- 覆盖正常/边界/异常。
- 一个用例一个断言主题。
- 可重复、无外部依赖。
- 失败信息能定位。

## 5. 静态与动态分析

```bash
gcc -Wall -Wextra -Werror -fsanitize=address,undefined -g prog.c
clang-tidy src/*.c -- -Iinclude
cppcheck --enable=all --inconclusive .
scan-build make
```

| 工具 | 发现 |
|---|---|
| 编译器警告 | 类型/未初始化/未使用 |
| clang-tidy | 风格/缺陷/现代化 |
| cppcheck | 越界/泄漏/逻辑 |
| ASan/UBSan | 越界/UB |
| valgrind | 泄漏/竞态 |
| fuzz | 输入健壮性 |

## 6. 代码评审

- 小 PR（<400 行）更容易评审。
- 先看设计/边界，再看风格。
- 检查：失败路径、资源、并发、输入校验、日志、测试。
- 评审意见对事不对人；作者响应/记录。

## 7. 度量（谨慎使用）

| 指标 | 用途 | 风险 |
|---|---|---|
| 覆盖率 | 找未测路径 | 追求数字会写无用测试 |
| 圈复杂度 | 找难维护函数 | 不等于 bug |
| 缺陷密度 | 质量趋势 | 统计口径 |
| MTTR | 修复效率 | 依赖流程 |

## 8. 嵌入式约束

- 无 MMU/内存小：避免动态分配/大栈。
- 实时：避免阻塞/长临界区。
- 交叉编译：单元测试可在主机跑纯逻辑。
- 硬件依赖：用 mock/HAL 隔离。

## 9. 技术债

- 记录：位置/原因/影响/计划。
- 不把“临时补丁”伪装成最终方案。
- 每次改动顺手还一点，避免集中爆炸。

## 10. 检查表

- [ ] 边界/失败路径覆盖。
- [ ] 资源释放/无泄漏。
- [ ] 并发共享有保护。
- [ ] 输入校验/权限。
- [ ] 日志可定位、无敏感信息。
- [ ] 单测/静态分析通过。
- [ ] 评审记录。
