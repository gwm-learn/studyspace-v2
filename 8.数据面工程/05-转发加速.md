# 转发加速

> 解决什么问题：为什么软件转发只有几百 Mbps，而标称千兆/2.5G；怎么开、怎么验证、有什么坑。
> 不解决：具体 SoC 的寄存器与驱动细节（需厂商文档）。

## 1. 软件转发路径

```text
网卡收包 → NAPI → 协议栈 → 路由查找 → conntrack → NAT → 邻居 → 网卡发送
```

每个包都要走一遍，CPU 占用随 PPS 线性上升。小包（64B）最先打满。

| 瓶颈 | 表现 |
|---|---|
| 中断/软中断 | `ksoftirqd` 高、`softirq` 占比高 |
| 路由/conntrack | `nf_conntrack` 表大、查找慢 |
| 内存拷贝 | `skb` 分配/拷贝 |
| 单核 | 一个流打满一个 CPU |

## 2. 常见加速手段

| 手段 | 原理 | 层级 |
|---|---|---|
| flow offload | 首包走协议栈，后续包走流表短路 | 内核 |
| HNAT | 厂商硬件 NAT，直接改写/转发 | SoC |
| PPE | Packet Processing Engine，硬件转发 | SoC |
| DSA | 交换机端口直通，减少 CPU 参与 | 交换机 |
| RSS/多队列 | 多核分摊收包 | 网卡/驱动 |
| XDP/eBPF | 驱动层早期处理 | 内核 |

## 3. flow offload

```bash
# 查看是否启用
cat /proc/sys/net/netfilter/nf_conntrack_* 2>/dev/null
nft list ruleset | grep -i flow
uci show firewall | grep -i offload
```

OpenWrt 通常在 `firewall` 配置中：

```uci
config defaults
    option flow_offloading '1'
    option flow_offloading_hw '0'
```

要点：
- 首包仍走慢路径，流表建立后加速。
- 与 QoS/TC、复杂 NAT/ALG、抓包可能冲突（包被短路，tcpdump 看不到）。
- 硬件 offload 需要驱动支持，且对 VLAN/PPPoE/加密流量的支持因平台而异。

## 4. 验证方法

```bash
# 吞吐
iperf3 -c server -t 30 -P 4

# CPU/软中断
top -H
mpstat -P ALL 1
cat /proc/softirqs

# 流表/conntrack
conntrack -L | wc -l
cat /proc/net/nf_conntrack | wc -l

# 中断分布
cat /proc/interrupts
```

对比：关闭/开启 offload 各测一次，记录吞吐、CPU、时延。

## 5. 常见坑

| 现象 | 原因 |
|---|---|
| 开了 offload 抓不到包 | 后续包不走协议栈 |
| QoS 失效 | offload 绕过 tc |
| NAT 回流/端口映射异常 | 硬件流表未处理该场景 |
| PPPoE 加速无效 | 驱动/固件不支持 |
| 小包性能差 | 加速对小包收益有限，PPS 仍是瓶颈 |
| 温度升高 | 硬件加速单元功耗 |

## 6. 选型建议

1. 先确认瓶颈：是带宽、PPS、CPU 还是无线。
2. 软件转发够用就不要开硬件加速（可观测性更好）。
3. 需要千兆以上/NAT 高并发时，再评估 HNAT/PPE。
4. 开加速必须回归：NAT、端口映射、QoS、VLAN、PPPoE、IPv6、抓包。
